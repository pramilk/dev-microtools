  A Unix timestamp counts the seconds elapsed since midnight UTC on 1 January 1970. It is

faq:
  - q: Is my timestamp in seconds or milliseconds?
    a: Count the digits. A present-day timestamp in seconds has ten digits; in milliseconds it has thirteen. This tool auto-detects using that rule, treating anything of magnitude one trillion or more as milliseconds. Mixing the two up by a factor of a thousand is an extremely common bug — a seconds value read as milliseconds lands in January 1970.
  - q: Why does the displayed local time differ from what I expected?
    a: The local time row uses your computer's time zone setting, while the ISO and RFC rows are always UTC. If they seem inconsistent, check your system's time zone. A Unix timestamp itself carries no time zone at all — it is always an absolute moment, and the time zone only affects how it is displayed.
  - q: What are FILETIME, .NET ticks and WebKit timestamps?
    a: They are the same idea as a Unix timestamp with a different starting date and unit. Windows FILETIME (also used by LDAP and Active Directory) counts 100-nanosecond intervals since 1 January 1601; .NET ticks count the same intervals since 1 January 0001; Chrome's WebKit time counts microseconds since 1601; Apple's Cocoa time counts seconds since 1 January 2001. Their values are large enough to overflow a normal JavaScript number, so the converter does the arithmetic with big integers to stay exact. Pick the format explicitly - they are never auto-detected, because their ranges overlap Unix values.
  - q: Why does auto-detect only cover Unix formats?
    a: Because a Windows or .NET value and a Unix nanosecond value can have the same number of digits and mean completely different dates. The converter reads 10 digits as seconds, 13 as milliseconds, 16 as microseconds and 19 as nanoseconds, which is right for any present-day Unix value, and leaves everything else to the format list.
  - q: What happens after the year 2038?
    a: Systems that store timestamps in a signed 32-bit integer overflow on 19 January 2038, wrapping to a negative number and appearing to jump back to 1901. This is the "Year 2038 problem". Modern systems use 64-bit values and are unaffected for billions of years. This tool handles any value JavaScript can represent as a date.
  - q: Can I convert a date from before 1970?
    a: Yes. Timestamps before the epoch are simply negative — -86400 is 31 December 1969. The tool accepts negative values and converts them correctly, which is occasionally useful when working with historical dates in systems that store epoch values.
  - q: Does leap-second handling matter here?
    a: Not for Unix time. The Unix timestamp specification deliberately ignores leap seconds, treating every day as exactly 86,400 seconds. This means Unix time is not a true count of elapsed SI seconds since 1970, but it does keep the arithmetic simple and consistent, which is the trade-off nearly every system has chosen.

## ISO 8601 is the format to prefer

When you control the format, write dates as ISO 8601 with an explicit UTC offset —
`2026-03-14T09:26:53Z`. It sorts correctly as a plain string, it is unambiguous about time
zone, and every language's date library parses it. Formats like `03/14/2026` are ambiguous
between American and European conventions and cause real bugs.

## A token's expiry is just an epoch value

A JWT's `exp`, `iat` and `nbf` claims are ordinary Unix timestamps in seconds. Paste one in
above to see the exact date, or decode the whole token — header, payload and all three time
claims — at once with the [JWT Debugger](/jwt-decoder/).
